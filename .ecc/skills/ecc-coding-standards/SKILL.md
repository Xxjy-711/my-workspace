# 编码规范与最佳实践（ECC 适配）

跨项目通用的编码约定基线。

## 何时激活
- 新建项目或模块
- 评审代码质量与可维护性
- 重构以遵循约定
- 强制命名、格式化、结构一致性
- 设置 lint / 格式化 / 类型检查规则
- 新成员 onboarding

## 代码质量原则

### 1. 可读性优先
- 代码被读的次数远多于写的次数。
- 变量与函数命名清晰。
- 自解释代码优于注释。
- 格式一致。

### 2. KISS（保持简单）
- 能工作的最简单方案。
- 避免过度工程。
- 不做过早优化。
- 易懂 > 炫技。

### 3. DRY（不重复自己）
- 公共逻辑提取成函数。
- 创建可复用组件。
- 避免复制粘贴式编程。

### 4. YAGNI（你不需要它）
- 需求之前不造功能。
- 避免投机式泛化。
- 只在需要时加复杂度。

## 命名规范

```python
# PASS：描述性命名
market_search_query = "election"
is_user_authenticated = True
total_revenue = 1000

# FAIL：含义不清
q = "election"
flag = True
x = 1000
```

## 不可变性（CRITICAL）
- 始终创建新对象，绝不原地修改。
- 需要变更时返回带修改的新副本。
- 用不可变数据结构/模式（如 Python 的 `frozenset`、tuple；函数式写法）。

## 文件组织
- 多小文件优于少大文件。
- 单文件 200–400 行为典型，上限 800 行。
- 按功能/领域组织，不按类型组织。
- 高内聚、低耦合。

## 错误处理
- 每层都处理错误。
- UI 层给用户友好提示。
- 服务端记详细上下文日志。
- 绝不静默吞错（不写空 except / 空 catch）。
- 不暴露内部堆栈给用户。

## 输入校验
- 系统边界校验所有输入。
- schema 化校验，fail-fast，错误信息清晰。
- 绝不信任外部数据。

## 代码质量检查清单
- 函数小（<50 行），文件聚焦（<800 行）
- 无深嵌套（>4 层就要重构）
- 正确的错误处理，无硬编码值
- 可读、命名良好的标识符

---
**记住**：这些是共享地板，不是详细框架手册。框架特定模式（React/后端/API 等）用对应的领域 skill。
