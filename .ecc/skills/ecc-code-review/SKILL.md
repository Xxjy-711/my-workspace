# 代码评审（ECC 适配）

源自 ECC 的 code-reviewer：写完代码立即自审，先枚举问题再修复。

## 何时激活
- 写完新代码或修改完代码之后
- 提交 / 提 PR 之前
- 重构之后
- 需要第二双眼睛看质量时

## 评审流程

### 1. 先枚举，后修复
先完整列出所有发现的问题与严重级别，不要边看边改。

### 2. 评审维度
按以下维度逐项检查：

**正确性**
- 逻辑是否自洽？边界情况是否处理？
- 错误路径是否覆盖？异常是否被吞？

**可读性与可维护性**
- 命名是否清晰自解释？
- 函数是否小（<50 行）？嵌套是否 ≤4 层？
- 是否有重复代码（DRY）？是否有死代码？

**架构与结构**
- 是否按功能/领域组织，高内聚低耦合？
- 是否符合项目既有模式？

**安全**
- 是否有硬编码密钥？
- 输入是否校验？是否有注入风险（SQL/XSS/命令注入）？
- 是否泄漏敏感信息？

**性能**
- 是否有明显低效路径（N+1 查询、无谓重复计算）？
- 是否有未用的大依赖？

**测试**
- 是否有对应测试？覆盖率是否达标？
- 测试是否测用户可见行为而非实现细节？

### 3. 严重级别与处置
| 级别 | 含义 | 处置 |
|------|------|------|
| CRITICAL | 会出错、安全问题、数据损坏 | 必须修复 |
| HIGH | 明显缺陷、明显反模式 | 必须修复 |
| MEDIUM | 可改进 | 尽量修复 |
| LOW | 风格建议 | 可选 |

### 4. 输出评审结论
```
CODE REVIEW
===========
Files:    [变更文件列表]
CRITICAL: [X] — 列表
HIGH:     [X] — 列表
MEDIUM:   [X] — 列表
LOW:      [X] — 列表
Conclusion: [APPROVE / NEEDS WORK]
```

## 评审纪律
- 逐个 diff 检查，不遗漏变更文件。
- 发现 CRITICAL/HIGH 必须修复后再交付。
- 修复后重跑相关验证（测试/lint/build）。
- 不把「没检查过」说成「没问题」；结论不超过检查范围。

---
**记住**：评审不是走形式，是质量门禁。宁可多发现问题，不要放过问题。
