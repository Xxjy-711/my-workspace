# 测试驱动开发工作流（ECC 适配）

确保所有代码开发遵循 TDD 原则并获得全面测试覆盖。

## 何时激活
- 编写新功能/新逻辑
- 修复 bug
- 重构既有代码
- 新增 API 端点
- 创建新组件
- 接续某个实施计划继续开发

## 核心原则

### 1. 测试先于代码
**始终先写测试，再写让测试通过的最小实现。**

### 2. 覆盖率要求
- 最低 **80%** 覆盖率（单元 + 集成 + E2E）
- 所有边界情况覆盖
- 错误场景要测
- 边界条件验证

### 3. 测试类型
- **单元测试**：单个函数、工具、组件逻辑、纯函数。
- **集成测试**：API 端点、数据库操作、服务交互、外部 API 调用。
- **E2E 测试**：关键用户流程、完整工作流、UI 交互。

### 4. Git Checkpoint（在 git 管理下）
- 每个 TDD 阶段创建一个 checkpoint 提交，流程完成前不 squash、不改写。
- 推荐紧凑流程：
  - `test: add reproducer for <feature>`（RED 验证）
  - `fix: <feature>`（GREEN 验证）
  - `refactor: clean up after <feature>`（可选）
- 只有当前活动分支、可从当前 HEAD 到达的提交才算有效 checkpoint。

## TDD 步骤

### Step 0：检测测试运行器
不要假设 `npm test`。先确认项目的包管理器（npm/pnpm/yarn/bun）与测试运行器（Jest/Vitest/原生等），确定 `<test>`、`<coverage>`、`<lint>` 命令后再开始。

### Step 1：编写用户旅程
```
作为一个[角色]，我想要[动作]，以便[收益]
```
从计划文件中提取用户旅程与验收标准；计划未覆盖的部分再新写。

### Step 2：生成测试用例
为每个用户旅程创建完整测试用例，覆盖正常路径、边界情况、错误路径、回退行为。

### Step 3：运行测试（应当失败）= RED 门
```bash
<test>
```
- 只写但没编译/运行的测试不算 RED。
- 失败必须源于预期的业务逻辑 bug / 缺失实现，而非无关语法错误或依赖缺失。
- RED 确认前**不得修改生产代码**。
- git 下立即 checkpoint 提交。

### Step 4：实现代码
写最小代码让测试通过。git 下暂存最小修复，但 GREEN 确认前不提交 checkpoint。

### Step 5：再次运行测试 = GREEN 门
```bash
<test>
```
同一测试目标重跑，确认之前失败的测试现在通过。**只有 GREEN 通过后才能重构。**
git 下立即 checkpoint 提交。

### Step 6：重构
保持测试绿色的前提下：去重、改进命名、优化性能、提升可读性。
git 下立即 checkpoint 提交。

### Step 7：验证覆盖率
```bash
<coverage>
```
确认达到 80%+。

### Step 8：写 TDD 证据报告
推荐路径：`docs/testing/<task>.tdd.md` 或 `.github/tdd/<task>.tdd.md`。内容包括：
1. **源计划** — 引用的计划文件，或说明旅程来源。
2. **用户旅程** — 来自计划或本次新写的列表。
3. **任务报告** — 每个行为的执行摘要、实际运行的验证命令、相关输出片段（含 RED/GREEN 结果）、通过测试保证了什么。
4. **测试规格表**：
   ```markdown
   | # | 保证什么 | 测试文件/命令 | 测试类型 | 结果 | 证据 |
   |---|---------|--------------|---------|------|------|
   ```
5. **覆盖率与已知缺口** — 覆盖率命令/结果、有意的缺口、跳过的测试、未测的后续项。
6. **合并证据** — 若 checkpoint 会被 squash，把 RED/GREEN/refactor 摘要复制进 PR 体或 squash 提交体。

保持报告事实性：引用真实命令和结果，不编造未运行的 PASS。

## 常见测试错误
- **错**：测试内部实现细节（`component.state.count`）。
- **对**：测试用户可见行为（`screen.getByText('Count: 5')`）。
- **错**：脆弱的 CSS class 选择器。
- **对**：语义化选择器 / `data-testid`。
- **错**：测试互相依赖（前一个测试的数据被后一个用）。
- **对**：每个测试独立准备自己的数据。

## 最佳实践
1. 先写测试（TDD）
2. 单测单断言
3. 描述性测试名
4. Arrange-Act-Assert 结构
5. Mock 外部依赖，隔离单元测试
6. 测边界：null、undefined、空、大值
7. 测错误路径
8. 测试要快（单元测试 <50ms 每个）
9. 测试后清理副作用
10. 复盘覆盖率报告找缺口

## 成功度量
- 覆盖率 80%+
- 全部测试通过（绿）
- 无跳过/禁用测试
- 单元测试快速
- E2E 覆盖关键用户流程
- 测试在进生产前拦住 bug

---
**记住**：测试不是可选项，是能放心重构、快速开发、保障生产可靠性的安全网。
